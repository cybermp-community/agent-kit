# Надёжная поставка MCP и два сценария моддинга

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Цель** — дать установленному киту проверяемые ответы о CyberMP и довести два рецепта до явно зафиксированного уровня проверки.

**Устройство** — индекс типов и сведений собирается заранее, доставляется в npm-пакете и обслуживается существующими инструментами MCP. Первый этап проверяет установленный артефакт и безопасную настройку. Второй проверяет поиск и происхождение сведений. Третий проверяет рецепты в пределах доступной среды.

**Технологии** — TypeScript, ts-morph, MiniSearch, Vitest, MCP SDK и pnpm. Для игрового этапа нужны WolvenKit и CyberMP.

**Спецификация** — [Достоверность ответов CyberMP Agent Kit](../specs/2026-11-20-installed-mcp-and-modding-workflows-design.md).

## Общие ограничения

- Сохранить пять публичных инструментов, существующие аргументы и псевдонимы, штатный CLI и заявленную поддержку Node 20/22. Совместимость проверяется на поддерживаемых версиях CI.
- Не изменять Gangwar и Freeroam, не публиковать пакет и не устанавливать моды на пользовательскую машину в рамках этого плана.
- Существующие справочники включаются в инвентаризацию. Ручная проверка в первом цикле охватывает утверждения, влияющие на два пилота.
- Игровой результат и сборка архива фиксируются только после соответствующей проверки. Задачи MCP и CLI выполняются без игры.

## Что обязательно проверить при ревью

- Существующий JSON пуст, повреждён или содержит массив вместо объекта. Тесты задачи 1 проверяют сохранение байтов даже с `--force`.
- Рабочий проект содержит другую редакцию `game.d.ts`. Тест задачи 3 проверяет одинаковую установленную выдачу с этой декларацией и без неё.
- У native-класса есть собственные методы, у его предка есть перегрузки, а сокращённое имя совпадает с несколькими классами. Задача 2 проверяет наследование и неоднозначность.
- Врезка с ограничением находится дальше первых 500 символов. Задача 4 проверяет сохранение содержательного ответа и полного примера.
- Официальная синхронизация получила только часть входных файлов. Задача 5 проверяет ненулевой код выхода и сохранение предыдущего индекса.

## Этап 1. Поставка и установщик

### 1. Изолировать `init` и сохранить существующую конфигурацию

**Файлы** — `src/cli/init.ts`, `bin/cli.ts`, `README.md`, `tests/cli.test.ts`.

**Интерфейс** — `InitOptions.globalAntigravity?: boolean` соответствует флагу `--global-antigravity`. Выбор редактора Antigravity записывает правила проекта. Флаг отдельно разрешает глобальную запись. Существующий программный параметр `geminiConfigDir` задаёт каталог для явной глобальной операции и сохраняет уже поддерживаемые вызовы, которые передавали его в качестве явного места записи.

- [ ] Изолировать все тесты. Добавить проверки `default_init_does_not_touch_global_config`, `invalid_config_keeps_original_bytes_even_with_force` и `force_replaces_only_cybermp_entry`. Проверить также `null`, массив, пустой файл и невалидный контейнер настроек. Каждый глобальный путь в тестах находится во временном каталоге.
- [ ] Запустить `pnpm exec vitest run tests/cli.test.ts`. Подтвердить ожидаемые сбои на текущем поведении, используя только изолированные файлы.
- [ ] Убрать неявные глобальные записи, проверить формы корня и контейнера MCP, обновлять JSON через временный файл в том же каталоге и `rename`. При ошибке сообщать путь. Если существующая запись сохраняется, не переписывать JSON. Сохранить режим файла при замене. Обновить помощь и пример явной настройки.
- [ ] Запустить CLI-тесты и `pnpm run build`. Подтвердить, что настройка плагина и копирование skill работают без доступа к домашнему конфигу.

### 2. Поставлять native-индекс из lockfile

**Файлы** — новый `scripts/build-native-index.ts`, новый генерируемый `src/data/native-types.json`, `scripts/build-index.ts`, `src/types/index.ts`, `src/engine/types-engine.ts`, `tests/build-index.test.ts`, `tests/engine.test.ts`.

**Интерфейс** — `NativeTypeIndex` хранит `packageVersion: string` и `types: TypeRecord[]`. `MethodRecord` и `PropertyRecord` допускают поле `declaredIn?: string` для унаследованных членов. Сохранить `getTypeInfo(name, env?)` и существующий экспорт `parseRedengineType`. Парсер сборки принимает путь к установленному пакету, считывает версию и декларацию из него.

- [ ] Добавить проверки TS-фикстуры с собственным методом дочернего класса, унаследованным свойством, статическим методом, перегрузками и двумя совпадающими сокращёнными именами. На фактическом индексе проверить `segmentsNumber`, три перегрузки `SetTintColor` с владельцем `inkWidget` и отсутствие клиентского `MpCef` при `env: server`.
- [ ] Запустить `pnpm exec vitest run tests/build-index.test.ts tests/engine.test.ts`. Проверить, что новые случаи выявляют старое поведение.
- [ ] Сгенерировать компактный индекс из деклараций через AST без размножения унаследованных записей. Отсортировать типы, сохранить порядок перегрузок, разрешать предков при чтении и обрабатывать цикл наследования. Для неоднозначного сокращения вернуть варианты с полными именами. Убрать чтение деклараций из рабочей папки. Происхождение native-индекса показывать в выдаче.
- [ ] Повторить тесты и сборку. Сравнить результаты двух генераций из одинаковых входов. На этом этапе генерировать native-индекс отдельно, чтобы случайно не заменить текущий индекс руководств локальной неполной выборкой.

### 3. Проверить запускаемый tarball

**Файлы** — `src/server.ts`, `bin/cli.ts`, `README.md`, новый `tests/packed-mcp.test.ts`, `vitest.config.ts`, `.github/workflows/test.yml`, `package.json`.

**Интерфейс** — тест создаёт и извлекает tarball, устанавливает только production-зависимости в изолированную директорию, соединяется с CLI из `package.json#bin` через `StdioClientTransport` и завершает дочерний процесс. Отдельная команда `pnpm run test:packed` запускает проверку через отдельный проект Vitest. Обычный `pnpm test` не устанавливает зависимости и не требует сети. Использовать подготовленные зависимости CI или локальный кэш npm. Отсутствие нужного кэша сообщать отдельно от результата MCP.

- [ ] Зафиксировать регрессионную проверку `pack_lists_five_tools_and_reports_package_version`. Сравнить native-ответы в пустом рабочем каталоге и в каталоге с подставленной другой декларацией. Проверить `inkCircleWidget`, `SetTintColor`, источник версии и `MpCef` с `env: server`.
- [ ] Подтвердить на исходном tarball расхождение версии и отсутствие native-типов, как в аудите. Измерить размер архива и медиану времени от запуска транспорта до инициализации по одинаковой серии запусков до и после.
- [ ] Получать версию MCP из того же `package.json`, что и CLI. Исправить README по фактическим инструментам и поставке. Подключить изолированную проверку в CI.
- [ ] Запустить `pnpm test`, `pnpm run build` и проверку tarball. Зафиксировать фактические версии Node, размер, время запуска и результаты вызовов. Подтвердить отсутствие обращения к домашнему конфигу.

## Этап 2. Индекс и правила

### 4. Сделать поисковый ответ пригодным для выбора решения

**Файлы** — `src/types/index.ts`, `scripts/build-index.ts`, `src/engine/docs-engine.ts`, `src/engine/tweakdb-engine.ts`, генерируемые данные, `tests/docs-engine.test.ts`, `tests/tweakdb-engine.test.ts`, `tests/packed-mcp.test.ts`.

**Интерфейс** — `GuideRecord` дополнить полями `sourceKind`, `sourceRevision`, `environment`, `verificationStatus` и языком блока примера. Отсутствующую ревизию и сведения без доказательств обозначать явно. Формат ответа сохраняет текстовый MCP-контракт и дополняется выдержкой, статусом и рабочей ссылкой.

- [ ] Добавить фикстуру с ограничением после 500 символов и несколькими языками блоков. Проверить полноту короткого примера и ссылку для длинного. На фикстуре проверить, что неоднозначные `zone` и `polygon` различают HUD, большую карту, точечный маркер и серверную геометрию. Тесты против поставляемых рецептов добавляются в задачах 6 и 7.
- [ ] Реализовать индексацию полных разделов, ранжирование по символам и предметные синонимы RU/EN. Выдавать небольшую релевантную цитату рядом с ограничениями. Генерировать постоянные ссылки с ревизией там, где ревизия известна. Обозначить TweakDB как ограниченную подборку, сохранив существующие запросы.
- [ ] Запустить тесты поиска и TweakDB. Сохранить инвентаризацию по источнику, назначению и наличию проверки. Добавить в проверку tarball приёмочные запросы после появления рецептов.

### 5. Связать обновление корпуса, релиз и правила

**Файлы** — `scripts/sync-docs.ts`, `scripts/build-index.ts`, новый манифест источников в `src/data/`, `.github/workflows/{auto-update,release}.yml`, `rules/`, `templates/`, `skills/cybermp-dev/SKILL.md`, `tests/{sync-docs,workflows,skills}.test.ts`.

**Интерфейс** — манифест фиксирует ревизию upstream, перечень полученных файлов и точные версии пакетов типов. Правила редакторов и основной skill используют один канонический блок порядка проверки и ссылок.

- [ ] Проверить частичную загрузку и полную ошибку синхронизации. Тест требует ненулевой exit code, отсутствие смены набора рабочих данных и сохранение предыдущего индекса. Проверить две идентичные генерации и совпадение общего блока правил.
- [ ] Загружать входы в временную папку по фиксированной ревизии, сравнивать состав с манифестом до замены. Release собирает проверенный индекс из checkout. Обновление upstream проходит через проверяемый diff. Сверить условия распространения корпуса и заменить неясные заимствования собственными краткими сводками со ссылками.
- [ ] Убрать из инструкций гарантии, не поддерживаемые реализацией guard. Сохранить подключение правил в каждом редакторе и общее описание пяти инструментов. Заменить зависимую от абсолютного пути метрику «100% покрытия» проверками содержания пилотов.
- [ ] Запустить тесты синхронизации, workflow и skill, затем тесты tarball. Сверить, что индекс release не зависит от текущего состояния сети и upstream.
