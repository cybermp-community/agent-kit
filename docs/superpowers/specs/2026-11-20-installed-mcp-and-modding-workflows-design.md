# Достоверность ответов CyberMP Agent Kit

Проект спецификации от 20 ноября 2026 года. Исходная ревизия кита — `fc6e667`.

## Цель

Агент, запущенный в проекте разработчика, должен получать из установленного кита воспроизводимый ответ с указанием среды исполнения, версии источника и границ применимости. Первый цикл проверяет это на двух задачах: нативная зона на миникарте и оригинальный архивный проп, который используется из CyberMP API.

Контур работ включает MCP, сборку индекса, установщик, правила редакторов и поставляемые справочники. Gangwar и Freeroam служат источниками и объектами чтения. Изменять их, устанавливать моды на машину пользователя или публиковать пакет в рамках этой спецификации не требуется.

## Рассмотренные подходы

1. **Исправить установленный MCP и проверить два сквозных сценария.** Этот порядок выбрал пользователь. Исправления выпускаются небольшими порциями, у каждой есть отдельный критерий приёмки. Два сценария задают минимальный объём новой документации.
2. **Сначала исправить Markdown.** Это быстро помогает при ручном чтении справочников. Для такой же пользы через MCP всё равно нужны изменения индекса, выдачи и поставки пакета.

## 1. Установленный MCP и безопасная установка

- Собирать native-индекс из точной версии `@cybermp/client-types`, разрешённой lockfile, и включать его в tarball. Использовать синтаксическое дерево деклараций при сборке. В runtime читать поставляемый индекс без поиска `game.d.ts` в рабочем каталоге. Хранить собственные члены типа и связи наследования. Выдавать унаследованные члены с указанием владельца, сохранять перегрузки и разрешать сокращённое имя только при однозначном совпадении в выбранной среде. Начать с native-классов и интерфейсов из `game.d.ts`; добавить enum и другие формы в этот цикл, только если они требуются существующему контракту или двум сквозным сценариям.
- Сохранить пять имён MCP-инструментов, аргументы и текущие поддерживаемые псевдонимы. `env` ограничивает результаты типами выбранной среды и общими типами. При совпадении только в другой среде можно показать краткую подсказку о ней без подстановки сигнатуры в результат. Версия MCP при инициализации совпадает с версией пакета. Справка и README отражают фактическую поставку.
- `init -y` устанавливает файлы проекта. Глобальная настройка Antigravity требует отдельного явного выбора. Запись JSON выполняется после проверки, что существующий файл разбирается и его контейнеры имеют ожидаемый тип. При ошибке сообщить путь и сохранить содержимое. Сохранить посторонние настройки и пользовательские изменения. При конфликте существующей записи `cybermp` сохранить её без `--force`; при замене с `--force` сохранить остальные записи. Запись каждого обновлённого JSON должна быть атомарной. Возможность явно установить workspace-плагин сохраняется.
- Тестировать `init` на временных каталогах проекта и глобального конфига. Извлекать tarball в чистый каталог и запускать через штатный CLI с runtime-зависимостями. По `stdio` подтвердить пять инструментов, версию, `inkCircleWidget.segmentsNumber`, унаследованные перегрузки `SetTintColor` и отказ от выдачи клиентского `MpCef` по `env: server`. Повторить native-запросы из проекта с другой версией пакета типов. Результат должен сохранять версию индекса кита.

## 2. Индекс, выдача и источники

- У записи справочника хранить точный источник и ссылку, среду, применимость по версии при наличии и статус утверждения. Для автоиндексов хранить версию пакета или ревизию документации в общем манифесте. Для TweakDB указывать, что это ограниченная подборка, и добавлять происхождение записей по мере их проверки. Декларация, официальное руководство, наблюдение на игровой сборке и гипотеза — разные основания. У неизвестной версии или неподтверждённого утверждения должен быть явный статус.
- В первом цикле применить схему метаданных ко всему поставляемому корпусу и составить инвентаризацию по источнику, назначению и наличию проверки. Вручную сверить утверждения, влияющие на два пилотных сценария. Остальные материалы без достаточных доказательств явно пометить при выдаче. Ручная сверка остальных рекомендаций продолжается отдельными тематическими порциями после пилота, начиная с противоречий между официальной документацией, типами и примерами.
- Индексировать полные компактные разделы, назначения API и точные имена. Сохранять ограничения и язык примера. В MCP-ответе показывать релевантный текст, ограничения и доступную вне checkout ссылку на исходный раздел. Отдавать целый короткий пример, если он помещается в бюджет ответа. Для длинного дать описание и ссылку на полный пример. Неоднозначный запрос о зонах должен сначала объяснить различия между точечной меткой, HUD, большой картой и серверной геометрией и дать ссылки на соответствующие разделы. Для этой группы запросов добавить русские и английские синонимы. Общий перевод корпуса в объём этого цикла не входит.
- В правилах редакторов и skill из одного источника поддерживать короткий порядок действий: определить среду и версии, сверить сигнатуру и жизненный цикл, выбрать рецепт с подходящими предпосылками, проверить неизвестное на минимальном примере. Убрать обещание, что список известных чужих символов проверяет весь сгенерированный код. Общие названия инструментов и ссылки должны совпадать в поставляемых правилах.
- Сборка релиза использует проверенный индекс. Синхронизация upstream отдельно фиксирует ревизию и фактический состав входа. Пустая или неполная загрузка при обновлении не должна заменять опубликованный индекс и должна приводить к диагностируемому сбою. Генерация из одинаковых входов воспроизводима. Право на распространение заимствованного текста и примеров проверяется при добавлении источника. Когда условия неясны, использовать собственное изложение и ссылку.
- Приёмка через MCP из tarball. `minimap`, `zone`, `polygon`, `AddBlipForArea`, `AddBlipForCoord`, `SetTintColor`, `зона миникарты` и `world map polygon` возвращают применимые ответы либо явные границы подтверждённого. `archive`, `WolvenKit` и `ArchiveXL` ведут к маршруту упаковки и указанию зависимостей. Проверки должны проверять содержание ответа и отсутствие взаимоисключающих советов. Тест с поиском последнего слова в Markdown не служит условием приёмки.

## 3. Два сквозных сценария

### Нативная зона на миникарте

Исправить аналогию FiveM и описать четыре задачи по отдельности. `RegisterMappin` покрывает точечный маркер. Регулярная фигура через INK — эксперимент с HUD. Пользовательская большая карта может использовать CEF. Принадлежность точки серверной зоне вычисляется серверной геометрией. Документация сохраняет исходное ограничение Gangwar на покадровую отправку координат в CEF.

Сослаться на документированный API наблюдения CyberMP. Получение нужного контроллера, состояние HUD и цвета проверять на целевой сборке. Описать отдельно входные форматы перегрузок `SetTintColor` и источники сведений о них. Начальный пример должен показывать один виджет, один контейнер и один способ окраски, с удалением при выгрузке. Рецепт мировой привязки требует визуальной проверки в движении, при повороте, изменении зума и пересоздании HUD. Пока такой проверки нет, можно документировать наблюдение фигуры и метод проверки привязки. Не переносить из отчёта как гарантии предел количества фигур, причину поведения прямоугольника и универсальную невозможность динамического рендера на карте мира.

### Оригинальный архивный проп

Начать с пустого проекта. Готового пропа у пользователя нет. В рамках сценария подготовить исходник минимального оригинального ассета, например простой цветной куб с уникальным путём ресурса. Описать создание и импорт геометрии, необходимые ресурсы сущности и упаковку в WolvenKit. Использовать для теста собственные материалы или зависимости, которые разрешено распространять. Исходники примера должны позволять повторить сборку.

Собрать `.archive`, проверить ассет в одиночной игре, объявить точные пути в `resource.toml`, подтвердить доставку и загрузку на чистом CyberMP-клиенте, затем разрешить путь ресурса и создать объект через документированный API. Отличимая форма или цвет помогают визуально подтвердить, что клиент загрузил именно тестовый архив. Первый пример показывает локальный проп. Второй клиент нужен для отдельного заявления о сетевой синхронизации.

Развести установку модов в игровой каталог, поставку `file` конкретного ресурса, встроенный `core.files`, клиентский скрипт и CEF. Описать перезапуск клиента для изменений архивов и скомпилированного redscript и повторную упаковку для CDN, если он используется. Дать таблицу применимости для `.archive`, `.xl`, `.tweak`/YAML, `.redscripts`, REDmod, ArchiveXL, TweakXL, Codeware, RED4ext и CET. Документированная доставка формата, доступность загрузчика и результат на целевой сборке заполняются независимо.

## Сдача и порядок работ

1. Исправить первые воспроизведённые дефекты в поставке MCP и установщике. Прогнать сборку, тесты и проверку tarball. Сохранить результаты до и после изменения.
2. Исправить индекс и правила, проверить ответы по обеим темам. Зафиксировать проверенные источники, оставшиеся противоречия и пробелы по мере аудита корпуса.
3. Подготовить рецепты и исходники тестового ассета. Зафиксировать версии CyberMP, клиента игры, типов и инструментов, артефакт или ревизию и наблюдаемый результат. Проверки 1–2 выполняются без игры. Для сборки архива нужна среда WolvenKit с доступом к ресурсам игры, для проверки поведения нужен тестовый клиент. При недоступности среды подготовить исходники и шаги воспроизведения, отметив отдельно статус сборки, загрузки и игрового результата.

Имена файлов индекса, формат хранения и бюджет ответа выбираются при планировании. Отдельно измерить размер tarball и время старта до и после генерации native-базы. Сохранить поддержку заявленных версий Node, публичных аргументов и штатного CLI. Изменение формата базы внутри пакета допустимо.
